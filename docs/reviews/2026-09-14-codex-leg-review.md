# Verdict: NO-GO

The adapter implements the basic happy path, but it does not yet meet the approved plan's lifecycle and compatibility guarantees. Confirmed failures include accepting another turn's answer, losing the serialization guarantee after timeout, and an unhandled rejection on initialization failure. These findings are independent of the subprocess restrictions that prevented successful integration testing in this review environment.

# Blockers

1. **high — `src/turn-runner.ts:60`, `:169`, `:177`, `:210`: notifications are correlated only by thread, and timeout releases the thread before interruption completes.** `extractAgentMessage` ignores `params.turnId`; the completion handler never compares `turn.id` with the accepted turn ID. After a timeout, the old turn can still emit messages and completion while the next call has installed listeners. Those events can supply the next call's answer and terminate it. An in-memory probe of the actual source started turn `new`, delivered an item and completion for `old`, and received `{turnId:"old", status:"completed", text:"STALE"}`. Another probe left interruption requests unanswered and observed `turn/start → turn/interrupt → turn/start → turn/interrupt` on one thread. The promise chain at lines 119–134 correctly serializes ordinary calls: the map is updated synchronously before another caller reads it, and the next `runTurnOnce` waits for the preceding promise. However, settlement of a synthetic timeout is not proof that the upstream turn stopped. Correlate both IDs, buffer notifications arriving before the start response, and retain an upstream-busy/quarantined state until completion or bounded recovery establishes that another start is safe. Returning a timeout promptly must not require prematurely unlocking the upstream thread.

2. **high — `src/index.ts:47`: initialization failure creates an unhandled rejection despite the tool's catch.** `void promise.finally(...)` creates another promise that rejects when initialization rejects. Nobody handles that derived rejection. I invoked the actual lazy wrapper with a rejecting initialization double, caught the original rejection, and still observed `unhandledRejection: handshake failed`. With ordinary Node rejection handling this can terminate the MCP process, defeating the advertised recovery behavior. Handle cleanup on both settlement branches without leaving a rejected promise unobserved; close a child whose initialization fails. Add a failed-initialize/failed-spawn test through the entry point, not just a successful-child restart test.

3. **high — `src/turn-runner.ts:203`, `src/app-server-client.ts:101`, `:172`: the timeout does not bound request acceptance; its installation also races completion.** The timer starts only after `turn/start` responds. A live child that never answers `initialize`, `thread/start`, `thread/resume`, or `turn/start` can strand a tool call indefinitely; queue wait is also outside the turn timer. My 10 ms `runTurn` remained pending after 50 ms when `turn/start` never responded. Conversely, if completion is dispatched before the start promise's continuation runs, cleanup executes before the timer exists; the continuation then installs a timer for an already completed turn. A source probe reproduced a later `turn/interrupt` after successful completion. The transport dispatches all lines in a received chunk synchronously, so response and completion in one chunk can produce this ordering without an invalid protocol exchange. Bound setup/request waits, guard timer installation with settlement state, and distinguish “start acceptance unknown” from an accepted turn that can be interrupted. Exercise coalesced response/completion frames and unanswered start requests.

4. **medium — `src/turn-runner.ts:75`, `:88`, `:105`; `src/index.ts:28`, `:60`: restart handling omits remembered settings and generation-safe operation boundaries.** There is no settings map or generation counter. `startThread` remembers only the ID; `ensureThread` sends only its supplied fallback. Replacing the runner on child exit effectively discards the old known-ID set, but also loses settings for threads started in the still-running MCP process. Replies after a child restart therefore fall back to `never`/`read-only` instead of preserving remembered settings as specified. Additionally, each lazy method obtains a session separately: child exit between `ensureThread`/`startThread` and `runTurn` can send `turn/start` to a fresh child without resuming that thread. Concurrent calls to `ensureThread` for the same unknown ID can issue duplicate resumes outside the turn lock. Preserve settings across child replacement, deduplicate resume, and bind preparation plus turn execution to a session generation. A full MCP-process restart may appropriately lose memory and use safe defaults; that is different from child replacement. The required offline restart-and-resume test is absent: `tests/index.test.ts` starts a new thread after exit, while runner tests only resume against an initially fresh fake.

5. **medium — `src/turn-runner.ts:231`; `tests/turn-runner.test.ts`, unknown-request case: rejected server requests disappear from `declinedRequests`.** The dispatcher returns before recording any method absent from `DECLINE_RESPONSES`. This loses `item/tool/call` and future unknown requests even when their params identify the active thread; the test explicitly expects the incorrect empty list. A source probe confirmed it. Record rejected requests as well as recognized declines. Auth-refresh and attestation requests lack thread IDs in the checked schema, so define an explicit attribution/diagnostic policy for those session-level failures instead of silently losing them.

   **The wire-response coverage itself is correct by inspection.** `schema/ServerRequest.json` contains ten methods. Command/file approvals get `{decision:"decline"}`; permissions get `{permissions:{}}`; legacy exec/patch approvals get the object-shaped denied decision; user input gets `{answers:{}}`; elicitation gets `{action:"decline"}`. Dynamic tool calls, auth refresh, attestation, and future unknown methods fall through to `-32601` with the incoming ID. The schema makes both granted-permission fields optional, so `{permissions:{}}` is a valid empty grant, not a blocker. The approved plan's corrected object-shaped legacy denial supersedes the older amendment's stale string example. No currently enumerated request is simply dropped without a response by this dispatcher.

6. **medium — `src/tools.ts:161`; README, `compact-prompt`: compatibility is changed into a different instruction.** The adapter appends the compaction prompt to ordinary developer instructions, changing normal turn behavior and failing to configure compaction. Calling out the substitution in text does not preserve the old field's purpose. The checked schema exposes `compact_prompt` in `schema/v2/ConfigReadResponse.json:504`, and `ThreadStartParams.config` accepts overrides. Verify the supported config override route and its precedence against explicit `config`; otherwise reject this field clearly pending support. Do not turn a summarization template into an instruction for every normal answer. The existing test checks only that the result mentions `compact-prompt`, not the outgoing configuration or compaction behavior. Runtime behavior of the proposed config route was not tested here.

7. **medium — `src/app-server-client.ts:186`: UTF-8 decoding corrupts output at arbitrary pipe chunk boundaries.** Each Buffer is independently converted to UTF-8 before line assembly. Splitting a multibyte character between chunks inserts replacement characters even though the complete byte stream is valid. Invoking the actual parser with a JSON notification split inside `中` yielded `���`. Use a streaming decoder or set the stream encoding once, and test a multibyte split independently of newline framing. This affects non-English answers and potentially identifiers/paths carried in messages.

8. **low — `src/tools.ts:94`, `:153`, `:209`, `:245`: “threadId always present” and the uniform result claims are overstated.** Successful calls, failed/interrupted resolved turns, and rejected turns after successful thread creation retain the ID. Reply-handler exceptions also retain the supplied ID. But profile rejection has no `structuredContent`; failed initialization/thread creation has no `threadId`; SDK input validation can reject before the handler. Rejection results also omit `status`, `turnId`, and `declinedRequests`, losing any declines accumulated before child exit. These omissions are explicitly accepted by some tests, contrary to the blanket Task 6/7 claims. No real thread ID exists before creation: specify an honest unavailable/null-ID error variant instead of fabricating one, retain known IDs and diagnostics, and narrow the README promise or agree an explicit contract amendment. Separately, the reply refinement accepts an empty `threadId` plus a nonempty alias, but the handler's `??` selects the empty ID; normalize/reject empty identifiers. `cwd` is also accepted as any string although the plan specifies an absolute path.

9. **medium — `tests/protocol.test.ts:78`, `tests/fake-app-server.mjs:128`, `tests/index.test.ts:1`, `tests/live.smoke.test.ts:30`: the verification does not establish several claimed guarantees.** The drift tests validate outgoing requests, `initialized`, and seven response bodies, but only check method names for incoming server requests/notifications. The fake's `item/completed` omits required `turnId` and `completedAtMs`; direct AJV validation against the committed notification schema fails. This lets the missing turn correlation pass unnoticed. Validate the actual incoming fixtures, including all ten request variants, and test additions to the request union, not just continued existence of known names.

   The tests do contain meaningful assertions: happy/fallback/final text, failed status and error text, declined-method lists, RPC rejection, child-exit rejection, and normal FIFO timing. They mostly spawn a real fake process; there is no blanket mock of `AppServerClient`. Nevertheless, six of seven table cases only assert that the fixture exists, not that its exact body was returned on the wire; only the command-approval case checks the echoed body. The timeout test checks status and elapsed time but never confirms receipt/ID of the interrupt. The fake's `expect()` merely warns on a wrong method. Progress is tested only with a `TurnRunnerLike` stub and mocked `sendNotification`. Most tool tests bypass SDK parsing and manually supply defaults. Neither `index.test.ts` nor the live smoke launches the actual MCP entry point: the comment deferring stdio E2E to the live suite is inaccurate. Add real MCP-pipe tests for initialize/list/call, schema/default application, reply/error paths, progress, shutdown, and child failure/recovery. Add the offline restart/resume, late-event, byte-fragmentation, and failed-initialization cases above.

# tokensift comparison

I read the implementation, not just the brief's characterization. Its concerns are different: tokensift performs repeatable public HTTP reads; this adapter starts stateful, potentially costly agent turns.

| Pattern | Actual tokensift implementation | Applicability to codex-app-mcp |
|---|---|---|
| Uniform envelope, typed errors, model-facing advice | `models.py`, `errors.py`, `client.py`, and `server.py` define an output schema, convert domain exceptions, and return matching text/structured envelopes with `is_error`. Tests compare library and MCP results, including errors. | **Missing in part; worth adapting.** Keep the legacy text answer and thread metadata, but normalize error variants and preserve RPC code/diagnostics. Distinguish invalid input, child exit, start failure, and timeout with execution state unknown. This directly addresses blocker 8 and makes blockers 2–5 diagnosable. Copying the HTTP-specific enum verbatim would be misleading. |
| Per-provider rate limiting with bounded wait | `http.py` has an `AsyncLimiter` per provider; `_acquire` bounds waiting using `asyncio.timeout`. | **Provider buckets do not apply:** the wrapper does not call those providers. **Bounded waiting does apply:** setup and acceptance can currently hang, and same-thread queues have no deadline. Adopt a call/setup deadline and bounded queue admission as needed; do not add arbitrary HTTP-style RPM limits. |
| Separate success/negative TTL caches | Two bounded `TTLCache` instances; defaults are 30 s success and 10 s negative. HTTP `NotFound`/`InvalidInput` are cached; rate limit/unavailability are not. | **Inapplicable to turn results.** Identical prompts can mutate conversation state and produce different answers; caching them could skip execution or replay another state. A known-thread/settings map is lifecycle state, not a TTL answer cache. |
| One retry for 429/502/503/504 and `Retry-After` | `_request_with_retry` retries once; numeric retry delays are clamped to 0–5 s. HTTP-date values fall back to the default, so “honors Retry-After” is not universal. | **Do not replay `turn/start` automatically.** Lost acceptance can mean a turn already exists; replay could duplicate work. The app-server owns model retries, and the runner correctly does not terminate on `willRetry:true`. Recover sessions explicitly and make uncertain acceptance visible. Retry-after advice is useful only when an actual upstream signal establishes it. |
| Stderr-only logging | `server.main` configures stderr and disables the banner; pipe tests parse every stdout line as JSON-RPC. | **Already implemented in source.** Child diagnostics and wrapper diagnostics use stderr. Adopt the pipe test to verify the deployed entry point; no new logging framework is needed. |
| `verbose`-gated bounded raw output | `client.py` includes raw data only when requested; `_bound_raw` caps its compact JSON representation and marks truncation. | **Raw API payloads do not apply:** the adapter exposes final answers, not raw transport records. Avoid adding `verbose` solely for parity. Bounded diagnostics/frame handling would be sensible if introduced, and any answer truncation must be explicit and compatible with callers expecting a complete review. It would not fix the confirmed UTF-8 bug; streaming decoding does. |
| Dual-era handshake over a real pipe | `tests/test_stdio.py` explicitly sends legacy `2025-11-25` initialize/list messages and uses a modern FastMCP client in auto mode over stdio. | **The real-pipe testing pattern is worth adopting immediately** for blocker 9. The current live tests stop below the MCP boundary. Test the protocol eras actually required by the callers and supported by the Node SDK; do not add an independent dual-era implementation without that requirement. The modern test uses SDK auto negotiation rather than explicitly asserting the exact metadata version on the captured wire. |

Tokensift is not a flawless template. Its default advice for some parsing failures says to retry with verbose/raw, but the parse exception path returns `Envelope.failed` without raw data even when verbose is requested. Locally rejected invalid inputs also do not traverse the HTTP negative cache. These details reinforce borrowing tested ideas rather than copying README claims.

The adapter's overall split into transport, runner, and tool shaping is appropriate; shared decline literals and lazy startup are reasonable. There is no broad Phase 3 approval bridge, steering, or streaming feature creep. The unsupported `compact-prompt` reinterpretation is the clearest invented behavior. HTTP caching/retry/provider infrastructure would add scope without fixing the actual failures.

# Falsifier

The single strongest operational falsifier is a timed-out turn that finishes late after a second call starts on the same thread. If the first turn's final item/completion can reach the second call's listeners, the wrapper can return the first answer as the second result and release another turn while the real second turn remains active. The actual source already exhibits this under controlled event injection, and its timeout path allows the necessary overlap. Reproduce this over a spawned fake process and the real MCP pipe: delay interruption/completion, queue a second call, then deliver old-turn events. The implementation must neither misattribute the answer nor issue a new upstream start while the old turn remains unresolved. Until that test passes, a successful pong or connected-server listing does not establish correctness for long reviews.
